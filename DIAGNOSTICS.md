# Проект диагностики соединения MIGA

Диагностика соединения для [задачи № 13](https://github.com/exzod-ik/miga/issues/13). Авторизация серверных проверок выполняется через действующую сессию miga2.

## Запуск и результаты

Из вкладки VPS в MIGA Agent пользователь открывает отдельное окно диагностики, отмечает проверки флажками и запускает их последовательно. По умолчанию выбраны первые пять проверок. Подбор MSS и нагрузочный тест скорости включаются отдельно. Окно показывает текущий шаг, позволяет остановить сеанс, раскрыть наблюдения по каждому этапу и скопировать частичный или полный отчёт. Сбой одного шага позволяет продолжить независимые проверки. Для пропущенного шага выводится причина.

Agent работает вне перехвата. Для серверных проверок он получает одноразовый доступ через административный MigaProfiles-v2 и защищённое управление текущей сессии miga2. Статистика передаётся по отдельному TLS-каналу. Без подключения доступны локальные проверки перехвата и маршрута; серверные проверки пропускаются с указанием причины.

Тестовый трафик создаёт miga_diagnostics.exe на Windows. В режиме проверки туннеля служба подтверждает временный маршрут конкретного экземпляра процесса через выбранный VPS до открытия первого тестового сокета. При невозможности подтвердить маршрут зависимый тест пропускается. В режиме проверки правил действуют обычные правила классификации. Для проверки правила по имени приложения наблюдается соединение самого приложения. Временные настройки снимаются при завершении, отмене или аварийном прекращении сеанса, без записи в конфигурацию.

## Выбираемые проверки

| Проверка | Выполнение и результат |
|---|---|
| Перехват WinDivert | Сопоставить созданный поток с событием NETWORK и владельцем. Показать PID, имя приложения и факт перехвата. |
| Выбор маршрута | Показать решение для потока, наблюдавшегося в текущем шаге, выбранный сервер, основание решения либо причину сброса. Для проверки туннеля подтвердить маршрут через выбранный VPS. |
| Первое плечо, Windows ↔ VPS | Отправить нумерованные пробы через туннель встроенному ответчику VPS. Сопоставить завершение отправки, приём и ответ на VPS, получение на Windows. Вывести счётчики и время обмена. |
| TCP за VPS | Выполнить TCP-подключение и TLS-рукопожатие с внешним сервисом по подготовленному IPv4, проверяя сертификат по имени. Отдельно показать результат TCP и TLS, включая отказ и тайм-аут. |
| UDP за VPS | Отправить короткий STUN Binding Request на stun.cloudflare.com:3478/UDP. Проверить успешный ответ с соответствующим идентификатором транзакции. Показать узел, задержку и последнюю подтверждённую точку пути. |
| Подбор MSS | Последовательно проверить исходящее направление до VPS и сквозной маршрут до Cloudflare STUN. Вывести результаты каждого замера отдельно. |
| Скорость через VPS | Запустить M-Lab NDT7 в диагностическом процессе. Подбор узла через Locate API и оба замера идут по IPv4 через выбранный VPS с обычной настройкой MSS. Показать узел, город, загрузку и отдачу одного TCP-потока в Мбит/с. Перед запуском сообщить о публикации результатов M-Lab и сборе видимого выходного IP. |

Для коротких внешних проб VPS передаёт через управляющий канал IPv4 и имя узла. Ошибка подготовки адреса отображается отдельно от тайм-аута отправленной пробы. Сервер фиксирует успешную запись в TUN и получение соответствующего ответа из TUN. Отсутствие ответа само по себе не устанавливает место потери.

## Подбор MSS

На время этого шага MigaClient пропускает поля MSS в обоих направлениях для тестовых TCP-потоков без изменений. Размер измеряется с помощью UDP-проб. Начать с короткой контрольной пробы и постепенно увеличивать размер исходящего внутреннего IPv4-пакета. Во внешнем IPv4 установить DF и отключить ручную фрагментацию для проб. Для сквозного теста также установить DF во внутреннем IPv4 и сохранить его при выпуске из VPS.

Для первого плеча использовать ответчик MIGA. Для сквозного теста увеличивать STUN Binding Request с помощью атрибута PADDING, сохраняя адрес назначения в пределах одного замера. После первого тайм-аута остановить рост, повторить этот размер и проверить последний успешный. Если контроль тоже перестал проходить, отметить замер как прерванный. Учитывать соответствующий ответ, полученный на VPS, даже если обратная доставка на Windows не завершилась.

Показывать подтверждённый размер, проверенный неподтверждённый размер при наличии и направление. Для внутреннего IPv4-пакета размером N байт расчётный TCP MSS равен N − 40 байт при базовых заголовках IPv4/TCP. Короткий ответ не измеряет предел обратного направления. Глобальную настройку автоматически не менять.

## Выбор публичного STUN-сервера

Для проекта выбран stun.cloudflare.com:3478/UDP. Проверка 13 ноября 2026 года выполнена на Windows по IPv4 с DF. Для каждой успешной пробы проверены тип Binding Success Response и идентификатор транзакции.

| Проба | Полный размер STUN | Размер IPv4 | Успешные ответы |
|---|---:|---:|---:|
| Обычный Binding до и после больших проб | 20 байт | 48 байт | 2 из 2 |
| Сообщение с PADDING общей длиной 1400 байт | 1400 байт | 1428 байт | 2 из 2 |
| Значение атрибута PADDING длиной 1400 байт | 1424 байта | 1452 байта | 1 из 1 |

Все ответы были длиной 32 байта без PADDING. Проверка подтверждает приём запросов этих размеров в наблюдавшихся условиях. Следующая проверка при реализации — повторить пробы через выбранный VPS MIGA и подтвердить доставку без фрагментации на обоих плечах. Сквозной MSS через MIGA пока не измерен.

Cloudflare описывает публичный STUN как бесплатный сервис без лимита. Отдельное разрешение или гарантия для серий PMTU-проб с PADDING в проверенной документации не указаны. [Cloudflare Realtime FAQ](https://developers.cloudflare.com/realtime/turn/faq/) · [RFC 5780](https://www.rfc-editor.org/rfc/rfc5780.html) · [M-Lab Locate API](https://www.measurementlab.net/develop/locate-v2/) · [M-Lab NDT](https://www.measurementlab.net/tests/ndt/)

## Единицы обычных наблюдений

В разделе «Наблюдения Windows» JSON содержит `captured` — наблюдения перехваченных внутренних пакетов выбранного процесса, и `unowned` — наблюдения без владельца на зарегистрированных сокетах. Эти величины нельзя напрямую сравнивать со счётчиками внешних отправок.

`send_counter_unit=outer_send_batches` означает, что `submitted` считает попытки передачи внешних пачек через WinDivertSendEx для TCP и UDP. Одна пачка может содержать несколько IPv4-фрагментов. `completed` считает только полные успешные завершения; `send_rejected` включает немедленный отказ, переполнение пула и отмену. `pending=submitted-completed-send_rejected` показывает ожидающие завершения. Отказ до формирования отправки учитывается отдельно в `pre_send_rejected`, во внутренних пакетах. Завершения предыдущего сеанса регистрации не попадают в новый сеанс. Успешное завершение WinDivertSendEx не доказывает приём на VPS или доставку внешнему узлу.

`tun_response` сопоставляется по виртуальному адресу, протоколу и полному транспортному потоку; TCP дополнительно проверяется по sequence/ACK, STUN — по transaction ID. Порты сопоставляются в порядке байтов хоста. Ноль этого счётчика в отчётах старой версии до исправления лишнего htons не доказывает отсутствие ответов из TUN.

## Настройка реализации

Вкладка VPS содержит кнопку «Диагностика соединения…». Agent запускает соседний miga_diagnostics.exe и передаёт параметры через стандартный ввод. Перехват и временный маршрут подтверждает MigaClient через локальный канал MigaDiagnostics-v1, доступный SYSTEM и администраторам. Каждый тестовый сокет регистрируется до Connect/Send. Завершение процесса или закрытие канала снимает сеанс. Пароли и параметры диагностики не сохраняются в клиентский JSON.

В окне остаются режим, PID приложения, семь флажков, запуск/остановка и отчёт. Полей TCP-порта, имени сертификата, PFX, CA и пароля больше нет. Кнопка «Настроить по SSH» удалена, установщик/обновление Agent не выпускает диагностические сертификаты через SSH.

Авторизованная сессия принимает DiagnosticOpen (13), возвращает DiagnosticReply (14): 2 байта TCP-порта big-endian, 32 байта SHA-256 DER-сертификата и 32 случайных байта одноразового билета. Ответ защищён персональными ключами управления v2. Запрос исполняется потоком управления клиента через ограниченный слот и дедлайн 8 секунд; NETWORK-поток не ожидает его. Административный pipe отдаёт Agent только параметры диагностики, без ключей приглашения.

DiagnosticControl создаёт в памяти собственный TLS-сертификат при старте. Agent проверяет точное совпадение SHA-256 с отпечатком из v2; доверие системному CA, имя SAN и клиентский сертификат для этого канала не используются. После TLS-рукопожатия первая команда authorize содержит билет. Без действительного билета диагностические команды не исполняются, соединение закрывается. Билет действует 30 секунд, используется один раз, привязан к сессии; очередь ограничена 64 билетами. TLS-сеанс ограничен 120 минутами, незавершённая авторизация — 10 секундами. Закрытие или отзыв сессии удаляет билеты и закрывает её диагностическое соединение. Наблюдения исходящих пакетов привязаны к сессии, входящие — также к виртуальному IPv4 наблюдаемого потока; общий внешний NAT-адрес не даёт доступа к чужим наблюдениям.

По умолчанию listener использует 47900/TCP; необязательный diagnostics.port меняет порт на VPS. Клиент узнаёт его автоматически. Сервер устанавливает собственное правило локального firewall и удаляет его при остановке; внешний firewall провайдера должен разрешать этот TCP-порт. Старые certificate/private_key/client_ca в конфиге не используются. Старый сервер без DiagnosticOpen не даёт ложного успешного результата: серверные проверки недоступны, локальные продолжаются. Нужны обновлённые Agent, Windows-служба и сервер; автоматического развёртывания нет.

Локальный begin выбирает профиль по profile_id. Если профиль отсутствует или сессия ещё не ready, служба регистрирует процесс без принудительного туннельного маршрута и возвращает local_only. Проверки capture/route работают с обычной классификацией, остальные пропускаются. Если выбраны только локальные проверки, серверный канал вообще не открывается. Измерение скорости также требует авторизации, чтобы прямой тест не выдавался за скорость через VPS.

Ответчик использует внутренний адрес 198.18.0.1:47901 и случайный 128-битный токен текущего диагностического сеанса. Ответчик принимает только пакеты авторизованной туннельной сессии. Встроенный DNS Windows исключает этот адрес из выдачи и подмены. Неактивная диагностика сохраняет быстрые атомарные проверки без диагностических блокировок и форматирования в обработке пакетов.

Проверки сборкой, loopback TLS и тестами с подменой API не подтверждают работу установленного WinDivert, публичных узлов и внешнего firewall. Для этого отдельно нужен разрешённый запуск на рабочем VPS.

### Статическая сборка OpenSSL для Release

Для распространяемого ELF следует использовать поддерживаемую OpenSSL 3.5 LTS. Проверенный релиз — 3.5.9; официальный архив: https://github.com/openssl/openssl/releases/download/openssl-3.5.9/openssl-3.5.9.tar.gz; SHA256: 603f5602e2eef00d77fbd429d34dcd5822bb301757a1bc9cdb24c670f1eb859a. Версия сверена с https://openssl-library.org/source/. Нужны gcc/g++, Perl, GNU make, tar и HTTPS-загрузчик. Библиотеки собираются под минимальную поддерживаемую glibc, без установки в системные каталоги.

~~~sh
mkdir -p Build/openssl-lts
cd Build/openssl-lts
curl --proto "=https" --tlsv1.2 -fL https://github.com/openssl/openssl/releases/download/openssl-3.5.9/openssl-3.5.9.tar.gz -o openssl-3.5.9.tar.gz
printf "%s  openssl-3.5.9.tar.gz\n" 603f5602e2eef00d77fbd429d34dcd5822bb301757a1bc9cdb24c670f1eb859a | sha256sum -c -
tar -xzf openssl-3.5.9.tar.gz
cd openssl-3.5.9
./Configure linux-x86_64 no-shared no-tests no-apps --prefix="$PWD/../install" --libdir=lib
make -j2 build_libs
make install_dev
~~~

При MSBuild задаются MigaOpenSslIncludeDirectory и MigaOpenSslLibraryDirectory — абсолютные пути на Linux toolchain к Build/openssl-lts/install/include и Build/openssl-lts/install/lib. Проект передаёт libssl.a и libcrypto.a после объектных файлов. После сборки readelf -d miga_server должен показывать отсутствие NEEDED для libssl.so и libcrypto.so. При распространении ELF включается LICENSE.txt точного релиза OpenSSL.

Для инструментальных UDP-прогонов клиентский `options.sequence_port` и серверный `watch.sequence16` включают учёт уникальных номеров 0–65535 в двухбайтовой полезной нагрузке UDP. В stats доступны клиентские `captured_sequences`/`completed_sequences` и серверные `received_sequences`/`written_sequences`. Обычные счётчики сохраняют количество обработок, включая дубликаты. Каждый прогон использует отдельную сессию и локальный порт, без повторного использования номеров. Захваты запускаются до отправки; после отправки ожидается затишье всех наблюдателей, затем неизменность счётчиков проверяется до и после остановки захватов. При изменении счётчиков окно считается недостоверным.

### Сетевые показатели VPS

При begin сервер сохраняет исходный снимок, а после выбранных проверок отдельная команда network_stats возвращает прирост за весь сеанс. Блок «Сеть VPS» показывает RX-кольцо и его максимум, SO_RCVBUF наблюдаемого сокета MIGA (если источник доступен), RX/TX packets, drops/errors интерфейса, доступные RX drops/errors драйвера (включая VMXNET3 pkts rx OOB), drops наблюдаемого сокета и softnet по CPU. Исчерпание бюджета softnet отмечается отдельно и не считается количеством потерянных пакетов.

Счётчики относятся ко всему интерфейсу/стеку/сокету, включая фоновые потоки. Их нельзя складывать или использовать как процент потерь конкретной пробы. Отсутствие источника, уменьшение счётчика, смена boot ID, интерфейса или сокета дают «нет данных», а не ноль. Старый сервер без команды network_stats остаётся совместимым, но сетевые показатели недоступны.

Чтение proc/sysfs и ethtool ioctl выполняется в потоке TLS-управления, без mutex пакетных наблюдений. На пакетном пути нет новых операций; фонового опроса и запуска внешних команд нет. Показатели не меняют кольца, буферы или системные настройки. Новые файлы: miga_server/include/DiagnosticNetworkStats.h, miga_server/src/DiagnosticNetworkStats.cpp, miga_diagnostics/ServerNetworkReport.cs.

## Проверка доступности UDP из MIGA Admin

После подключения по SSH откройте «Диагностика сервера» и запустите проверку UDP. По умолчанию VPS выбирает свободный порт (значение 0). Чтобы проверить конкретный порт, укажите свободный UDP-порт от 1024 до 65535. Для запуска на VPS нужны Python 3 и утилита `timeout`. Правила межсетевого экрана при проверке не меняются.

MIGA Admin передаёт временный скрипт по SSH и ждёт подтверждения, что тот открыл UDP-порт. Затем Admin отправляет пять пронумерованных датаграмм с интервалом 100 мс. VPS ждёт все пять пакетов до трёх секунд. Если дошёл хотя бы один, VPS отправляет пять ответных датаграмм на IP-адрес и порт отправителя. В результате отдельно видны потери по пути к VPS и обратно. Если VPS не получил ни одной датаграммы, обратное направление проверить невозможно. После завершения скрипт удаляется.

## Ступенчатая нагрузка и UDP-пинг

В окне диагностики доступны «Потери под нагрузкой» и «UDP-пинг до VPS». Главное окно Agent не изменяется. Нагрузочный тест работает только в режиме проверки туннеля и только через авторизованную MIGA v2, без прямого сравнительного прогона.

По умолчанию: 100, 250, 500, 1000, 1500 и 2000 пакетов/с, каждая ступень 60 секунд, UDP payload 64 байта, один повтор. Сначала Windows → VPS, затем VPS → Windows. Настраиваются длительность 1–300 секунд, payload 32–1200 байт, 1–5 повторов и до 12 строго возрастающих ступеней до 10000 пакетов/с. Общая расчётная длительность ограничена 90 минутами. После каждой ступени отводится 5 секунд на доставку, затем снимаются счётчики и проверяется их неизменность повторными снимками с интервалом 500 мс (до 3 дополнительных секунд). Нестабильное окно явно помечается предупреждением; более поздние пакеты не принадлежат следующей ступени.

Тестовая полезная нагрузка содержит 32-байтовый заголовок: MGL2, случайный идентификатор прогона uint64, ступень uint32, номер uint32, направление uint8, резерв. Числа big-endian. Заголовок находится внутри обычного зашифрованного туннельного пакета; wire format MIGA не меняется. На каждом этапе учитываются уникальные номера, повторы, перестановки и ошибки. Битовые карты ограничены rate × seconds, не более 3 миллионов номеров на ступень; попакетного логирования нет.

При отдаче таблица показывает: приложение Windows отправило → клиент перехватил → выбрал туннель → WinDivert подтвердил отправку → сервер MIGA принял → записал в TUN → UDP-приложение VPS получило. При приёме: приложение VPS отправило → сервер прочитал из TUN → UDP-сокет подтвердил отправку → клиент MIGA принял → WinDivert подтвердил reinject → приложение Windows получило. Подтверждение API не доказывает физический выход пакета из сетевой карты. Разница между соседними этапами и общий процент потерь рассчитываются относительно фактически отправленных уникальных пакетов, а не заданной нагрузки.

Отчёт содержит фактическую частоту, скорость payload, недоставленные пакеты, errors/duplicates/reordered и секундные группы номеров для всех этапов. Секундные группы соответствуют плановому времени отправки sequence/rate, а не синхронизированным часам прихода на двух машинах. Отдельно показаны опоздания генератора более 10 мс, фактический SO_RCVBUF, SO_RXQ_OVFL тестового сокета VPS и прирост сетевых показателей за ступень. SO_RXQ_OVFL сообщает значение вместе с принятым пакетом: drops после последнего полученного пакета могут ещё не попасть в снимок. Общесистемные счётчики включают фоновый трафик, могут перекрываться и не складываются с потерями теста.

На VPS создаётся временный обычный UDP-сокет на IPv4 сервера и порту выше 15000 с фактическим SO_RCVBUF не менее 8 МиБ. Проба проходит настоящий TUN и ядро до сокета. Узкое правило INPUT разрешает этот порт только с tun_miga. Ответчик принимает только согласованный run/step и tuple, зарегистрированный авторизованной сессией. Команды load_prepare/load_start/load_stats/load_stop идут через защищённое управление диагностики. Закрытие TLS, отзыв сессии, остановка и завершение ступени прекращают работу и удаляют временное правило. Генератор ограничен длительностью ступени; аварийно оставшийся worker завершает обработку через seconds + 30 секунд, ресурсы освобождаются при закрытии управляющей сессии. Производственная конфигурация не меняется.

UDP-пинг использует защищённый токеном ответчик первого плеча VPS, один запрос в секунду, независимые отправку и приём. Показываются min/average/p95/max RTT, разброс соседних ответов, потери, ошибки, дубликаты, незавершённые запросы, временной ряд и график. Самостоятельная длительность 1–3600 секунд; при совместном выборе пинг работает весь нагрузочный тест. Пинг измеряет путь Windows → MIGA на VPS → Windows, включая очереди и обработку, без внешнего интернет-узла. Запрос без ответа к снимку старше 2,5 секунд считается потерянным, более свежий — незавершённым.

«Прямой UDP-пинг до STUN» по умолчанию выключен. Его можно запустить отдельно в любом режиме диагностики. Нужна запущенная локальная служба MIGA для подтверждения обхода туннеля в обоих направлениях, включая полный режим. Подключение к VPS, приглашение и управляющий канал TLS для этой проверки не требуются. В комбинированном прогоне прямая проверка выполняется первой.

Helper получает IPv4-адрес `stun.cloudflare.com` через системный DNS и отправляет один STUN Binding Request в секунду на UDP-порт 3478. Длительность 1–3600 секунд, по умолчанию 10. В отчёте видны отправленные запросы, подтверждённые ответы, тайм-ауты 950 мс, ошибки сокета, RTT и график. STUN видит исходящий публичный IP клиента. Обход ограничен временным UDP tuple тестового сокета, который служба проверяет по PID клиента именованного канала и таблице Windows. При завершении пробы или закрытии канала обход снимается.

Остановка окна прекращает helper; завершённые ступени остаются в отчёте, незавершённая ступень не выдаётся за полный замер. Полный отчёт доступен через «Скопировать отчёт». Для проверки реального пути нужны обновлённые клиент и сервер; сборка и изолированные тесты не подтверждают работу установленного WinDivert и производственной сети.

Проверки helper: `dotnet run --project miga_diagnostics/tests/LoadMeasurementTests.csproj -c Release` (лимиты, номера, потери, одновременные запросы локального канала), `LocalDiagnosticsTests.csproj` (локальные проверки без авторизации) и `ServerNetworkReportTests.csproj` (включая прирост за ступень). Дополнительный сетевой тест UDP-пинга с намеренно пропущенным ответом и дубликатом: `dotnet run --project miga_diagnostics/tests/LoadMeasurementTests.csproj -c Release -- --udp-loopback`; он требует работающего UDP loopback на Windows. На машине разработки 15.11.2026 этот прогон завершился таймаутом; независимая отправка UDP через Python на 127.0.0.1 тоже не была принята. Причина на хосте не установлена; служба и настройки не менялись.

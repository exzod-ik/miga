# Проект нового UDP-протокола MIGA

Дата фиксации и уточнения решений: 2026-11-14.

Статус: согласованный проект, без реализации. Документ не описывает текущий wire format и не разрешает изменение кода, установку или развёртывание. Остаточные детали спецификации и будущие проверки перечислены отдельно.

## Цель и границы

Выборочное перенаправление IPv4 TCP/UDP с Windows через Linux VPS. Внешний транспорт — IPv4/UDP, без HTTPS и перехода на AmneziaWG. Цель обфускации — убрать явный счётчик, постоянный управляющий порт, открытые маркеры протокола и одинаковые размеры коротких служебных сообщений. Устойчивость к DPI/ТСПУ требует отдельных испытаний; шифрование само по себе её не гарантирует.

Сохраняются WinDivert на клиенте, TUN, маршрутизация Linux и NAT на сервере. Обычные UDP-сокеты заменяют внешний raw-сокет сервера. Выбор приложений, IP и доменов, несколько настроенных VPS и существующие границы поддержки не пересматриваются этим проектом.

## Управление клиентами и приглашения

Администратор устанавливает сервер и управляет клиентами через SSH из MIGA Agent. Приглашённому пользователю SSH-доступ не нужен. Владение приглашением не даёт административных прав.

Администратор добавляет запись клиента с человекочитаемым именем. Сервер создаёт случайный постоянный ID записи и персональный секрет доступа размером 32 байта. Имя используется только для администрирования, не включается в приглашение и может изменяться без его перевыпуска. Пользователь самостоятельно задаёт название подключения в своём Agent.

Приглашение — одна строка `miga2:<base64url>`. Внутри кодируется компактный JSON:

- адрес сервера и управляющий диапазон;
- открытый ключ сервера для его проверки;
- общий секрет сервера для получения ключей расписания и обфускационной оболочки;
- ID записи клиента и персональный секрет доступа.

Имена полей, кодирование и проверки импорта определены ниже в согласованных деталях спецификации. Префикс `miga2:` существует только в приглашении и не отправляется открытым заголовком сетевого пакета. Формат подходит для копирования, импорта из файла и QR-кода; наличие всех этих интерфейсов не считается уже реализованным.

Agent получает приглашение через административный канал, администратор передаёт его пользователю, пользователь вставляет его в одно поле Agent. Приглашение является учётными данными: его секретные поля не логируются и не включаются в публичные отчёты.

Сессионные ключи шифрования не распространяются по SSH: они создаются при подключении. SSH используется администратором для управления записями и получения приглашений. Закрытый ключ сервера остаётся на сервере.

Для каждой записи администратор задаёт максимум одновременных подключений по приглашению. Значение 0 означает отсутствие ограничения именно у приглашения; общий лимит активных сессий VPS действует всегда. Отключение освобождает место после закрытия сессии; потерянная связь — после тайм-аута или явного завершения администратором.

Регистрации устройств нет: не вводятся постоянный ID устройства, аппаратная привязка, отдельные секреты устройств, счётчик когда-либо использованных устройств или список зарегистрированных устройств. Одно приглашение может использоваться на разных устройствах в пределах одновременного лимита. Новый вход не вытесняет произвольно существующее подключение. Восстановление действующей сессии подтверждается владением её секретами, а не идентичностью устройства.

Удаление клиента запрещает новые подключения и закрывает все его действующие сессии. Удалённый клиент может сохранить общий секрет и вычислять управляющие порты, но персональная авторизация больше не проходит. Ограничение подключений хранится на сервере и не является доверенным параметром приглашения.

## Управляющие и сессионные порты

Управляющий диапазон по умолчанию — UDP 10000–15000 включительно. Порт новых подключений вычисляется для каждого календарного дня UTC. Сервер и приглашённый клиент независимо получают его из номера дня UTC и ключа расписания. Предварительное соединение или авторизация для вычисления не нужны.

Используется обычный HMAC-SHA256:

```text
day = floor(unix_time / 86400)
digest = HMAC-SHA256(schedule_key, uint64_big_endian(day))
value = uint64_big_endian(digest[0..7])
port = range_start + value mod range_size
```

Для диапазона по умолчанию `range_size = 5001`. День кодируется восемью байтами big-endian; первые восемь байт HMAC интерпретируются как беззнаковое big-endian число. Совместные тестовые векторы входят в приёмку реализации. Редкое совпадение порта в соседние дни допустимо. Перестановки портов, таблицы расписания, разделение по чётности дня и специальное устранение повторов не используются.

Ключ расписания и ключ обфускационной оболочки выводятся из общего секрета с разными метками назначения. Один ключ не переиспользуется напрямую для обеих задач.

Переходное окно: следующий порт открывается за пять минут до полуночи UTC, предыдущий закрывается через пять минут после неё. Клиент может пробовать соседний день в этом окне. При совпадении номеров используется один listener; его нельзя закрыть, пока он нужен хотя бы одному действующему дню.

При скачке системных часов сервер пересчитывает действующие управляющие listeners. Таймеры сессий и ожиданий используют монотонное время. При отсутствии ответа клиент сообщает: «Сервер недоступен, приглашение недействительно либо расходится время». Без ответа сервера достоверно различить эти причины невозможно.

Каждая сессия получает отдельный обычный UDP-сокет на свободном порту 1024–65535 вне настроенного управляющего диапазона. Порт резервируется непосредственно успешным bind(); если он занят, выбирается другой. Разные сессии не разделяют один серверный сокет/порт. Клиент использует один локальный UDP-сокет для обмена с выделенным портом сессии; фактический внешний порт может менять NAT.

Смена суток не меняет рабочие порты и ключи действующих сессий. Обработка управления выполняется отдельно на текущем управляющем порту; специальное подтверждение рабочего адреса проходит через выданный сессионный порт.

## Формат и защита управления

Управляющие сообщения бинарные: версия, тип операции, ID запроса, длина содержимого и содержимое. Числовые поля используют сетевой порядок байт. Эти поля зашифрованы; открытого постоянного заголовка, версии, имени или ID клиента нет.

Максимальный размер управляющей UDP-датаграммы — 1200 байт полезной нагрузки UDP. Собственной фрагментации управления нет. Начальные сообщения дополняются до случайного размера 384–768 байт, когда содержимое помещается в этот диапазон; точное распределение и правила для более длинных сообщений фиксируются в wire-спецификации с сохранением максимума 1200 байт.

Первое сообщение и начальный обмен Noise находятся во внешней обфускационной оболочке XChaCha20-Poly1305:

```text
[случайный nonce оболочки: 24 байта]
[зашифрованный запрос и padding]
[тег оболочки: 16 байт]
```

Первый запрос внутри оболочки содержит ID клиента, время, ID запроса, первое сообщение Noise и HMAC-SHA256 на персональном секрете. HMAC связывает как минимум ID клиента, время, ID запроса и сообщение Noise; однозначное представление подписываемых полей определяется wire-спецификацией.

Сервер последовательно:

1. Проверяет внешнюю оболочку.
2. Находит запись клиента по скрытому ID и проверяет, что она действует.
3. Проверяет персональное доказательство, допустимость времени и повтор запроса.
4. Только после этого выполняет ответную часть Noise и отвечает.

Общий ключ оболочки не заменяет персонального доказательства: отозванный пользователь, знающий общий секрет, не должен получать ответы. Сессионный сокет до успешной проверки не выделяется.

Повтор допустимого запроса с того же внешнего адреса получает сохранённый ответ без новой сессии. Повтор с другого адреса молча отбрасывается; клиент начинает новый обмен. Запросы за пределами допустимого времени и устаревшие повторы отбрасываются. Краткосрочная история принятых запросов сохраняется между перезапусками, чтобы перезапуск не делал записанный запрос снова новым. Окно времени — ±120 секунд, история хранится 10 минут с пределом 1024 × max_sessions. После перезапуска старые запросы отклоняются; клиент начинает новый обмен. Подробные правила приведены ниже.

Оболочка и персональное доказательство являются дополнительным протоколом поверх Noise. Их композиция требует проверки; обычный Noise NK сам по себе не обеспечивает молчаливую персональную авторизацию до первого ответа.

## Защищённая инициализация и библиотеки

Основа — Noise_NK_25519_ChaChaPoly_BLAKE2s: клиент заранее знает открытый ключ сервера из приглашения, предварительная регистрация ключа клиента не требуется. Персональное право доступа проверяется описанным доказательством.

Выбраны зависимости:

- libsodium — криптографический генератор, ChaCha20 для данных и XChaCha20-Poly1305 для оболочки;
- Noise-C — реализация Noise NK с закреплённой ревизией.

Совместимость выбранных ревизий с Windows/Linux, поставка зависимостей и тестовые векторы проверяются при реализации. Выбор библиотеки не означает, что интеграция уже проверена или сама композиция протокола прошла аудит.

Последовательность подключения:

1. Клиент вычисляет управляющий порт и отправляет обфусцированное первое сообщение с персональным доказательством.
2. Сервер молча отклоняет неверные запросы; для допустимого запроса завершается Noise-обмен и авторизация.
3. После успешной авторизации сервер резервирует место в пределах лимитов и открывает рабочий UDP-сокет.
4. Через защищённый канал передаются порт, параметры сессии, первые виртуальные адреса и свежий случайный 32-байтовый секрет сессии, созданный сервером.
5. HKDF-SHA256 с разными метками получает из секрета ключи и префиксы направлений данных и отдельные ключи управления. Внутренние ключи библиотеки Noise нестандартным способом не извлекаются.
6. Клиент отправляет защищённое подтверждение на рабочий порт. Сервер проверяет его, запоминает фактические внешний IP и порт клиента и подтверждает готовность.
7. Начинается независимая передача датаграмм данных.

Управление аутентифицировано, его ключи отделены от данных. После подключения операции управления выполняются через текущий управляющий порт отдельным обработчиком. База клиентов и операции Noise не участвуют в обычной пересылке пакетов данных. Оболочка последующих сообщений и состояния рабочего сокета определены ниже в согласованных деталях спецификации.

## Пакеты данных и шифрование

Для данных выбран ChaCha20 IETF без Poly1305 и без другого тега аутентификации. Это не AEAD. Нет номера пакета, окна защиты от replay, подтверждения доставки или восстановления потерь средствами MIGA.

Формат UDP payload:

```text
[случайная часть nonce: 8 байт]
[зашифрованный внутренний IPv4-пакет + padding]
```

Полный 12-байтовый nonce:

```text
[постоянный префикс направления из сессии: 4 байта]
[случайная часть из датаграммы: 8 байт]
```

Nonce используется как последовательность байт без преобразования в целое число. Начальный счётчик блоков ChaCha20 для каждого пакета — 0. Случайная часть генерируется криптографическим генератором для каждого нового пакета. Для направлений клиент → сервер и сервер → клиент используются разные 256-битные ключи.

Один внутренний IP-пакет передаётся одной внешней UDP-датаграммой. Потери и перестановки не требуют синхронизации: каждый пакет расшифровывается независимо. Версия, ID сессии и байт типа в данные не добавляются. Сервер определяет сессию по выделенному сокету и согласованному внешнему адресу клиента.

Автоматической смены ключей по времени или количеству пакетов нет. Ключи действуют до завершения сессии; новое подключение получает свежие ключи. Префикс не снижает вероятность совпадения случайных 8 байт внутри одного направления сессии.

Без padding и фрагментации накладные расходы сверх исходного IP-пакета — 36 байт: 20 внешнего IPv4, 8 внешнего UDP и 8 nonce. Внутренний IPv4/TCP-пакет с одним байтом данных и без опций занимает с оболочкой 77 байт, без канальных заголовков.

## Padding, keepalive, MTU и MSS

Пусть L — длина внутреннего IP-пакета, B = L + 8 — минимальный UDP payload:

- если B < 256, итоговый размер выбирается равномерно между max(96, B) и 256 байт включительно;
- если B >= 256, padding не добавляется;
- доступный MTU ограничивает верхнюю границу; ради padding фрагментация не создаётся. Если нижняя граница не помещается, padding сокращается или не добавляется, исходные данные не обрезаются.

Заполнение случайное и шифруется. Получатель берёт настоящую длину из внутреннего IPv4 Total Length, проверяет её относительно буфера и отбрасывает хвост.

Keepalive отправляет только клиент, без ответа сервера. После исходящей активности выбирается случайный интервал простоя 30–60 секунд. Пользовательской настройки нет. После отправки самого keepalive выбирается следующий интервал; обычные данные заменяют необходимость служебной отправки.

Размер keepalive выбирается равномерно от 96 до 256 байт UDP payload с учётом MTU. Формат тот же, но расшифрованное содержимое намеренно не является IPv4-пакетом: версия IP отлична от 4. Сервер отбрасывает его до TUN. Отдельный байт типа не нужен.

Существующий настроенный предел MSS сохраняется с дополнительным учётом размера оболочки: для обычных IPv4/TCP-заголовков потолок — MTU первого плеча минус 76 байт. Опции заголовков и фактические длины также учитываются. Диагностический режим без переписывания MSS сохраняется.

Собственная фрагментация протокола v2 не вводится. Внешняя IP-фрагментация остаётся на существующем клиентском механизме и Linux. Длина UDP payload внешнего IPv4 не может превышать 65507 байт: слишком большой внутренний пакет нельзя молча обрезать. При превышении выполняется стандартная внутренняя IPv4-фрагментация, если DF не установлен; при DF пакет не обрезается и формируется допустимое правилами ICMP уведомление о необходимости уменьшения размера. Это не собственный формат фрагментов MIGA; подробности и проверка заголовков приведены ниже.

## Адресация, TUN и совместимость с другим VPN

Обычный UDP-сокет заменяет raw-сокет только во внешнем транспорте. Внутренние пакеты пересылаются через TUN и Linux NAT/conntrack.

При установке выбирается свободная частная IPv4-подсеть /16 для виртуальных адресов. Проверяются пересечения с адресами, маршрутами и доступной конфигурацией других VPN, включая AmneziaVPN. Выбранная подсеть сохраняется; при каждом старте заново не выбирается. Если свободной подходящей подсети нет, настройка завершается понятной ошибкой.

Каждому реально используемому локальному IPv4 клиента соответствует отдельный виртуальный IPv4 сессии. Тысячи соединений с одного локального IP используют один виртуальный IP. Неиспользуемые адаптеры не получают адресов. Первый адрес выдаётся при подключении, дополнительные — защищённой операцией ADD_ADDRESS. Повтор запроса возвращает прежнее отображение.

Раздельные отображения сохраняют различие потоков с одинаковыми портами и адресатами, но разными локальными IP. Виртуальные адреса разных активных сессий не пересекаются.

Путь запроса:

```text
Приложение → WinDivert → подмена локального IP виртуальным → ChaCha20 → UDP
UDP-сокет VPS → расшифровка и проверки → TUN → Linux NAT/conntrack → интернет
```

Путь ответа:

```text
Интернет → Linux NAT/conntrack → TUN → поиск сессии по виртуальному IP → ChaCha20 → UDP
Клиент → расшифровка → восстановление локального IP → WinDivert → приложение
```

MIGA хранит отображения адресов и сессий. Собственные серверные таблицы NAT по каждому TCP/UDP-потоку, пулы преобразованных портов и соответствующее отслеживание TCP заменяются Linux conntrack. Системные маршруты и состояние NAT не исчезают.

После расшифровки проверяются длины, IPv4 IHL, Total Length, допустимый протокол и принадлежность исходного виртуального адреса сессии. После изменения заголовков пересчитываются контрольные суммы. Существующие правила DNS и маршрутизации не меняются без отдельного решения.

Для сосуществования с другим ПО:

- создаются только собственные интерфейс, цепочки и наборы firewall MIGA;
- NAT ограничен виртуальной подсетью MIGA и выбранным выходным интерфейсом;
- чужие интерфейсы, маршруты и правила не изменяются, политики цепочек по умолчанию не переписываются;
- конфликт адресации повторно проверяется при запуске; рабочая подсеть автоматически не меняется;
- совместимость с конкретной установкой AmneziaVPN проверяется отдельно, включая policy routing и Docker при его наличии.

## Жизненный цикл, восстановление и лимиты

| Параметр | Согласованное решение |
|---|---|
| Незавершённое подключение | 30 секунд |
| Сессия без входящих пакетов клиента | 5 минут |
| Повторные попытки управления | Через 1, 2, 4 и 8 секунд со случайным отклонением |
| Максимум активных сессий VPS | Настройка max_sessions, по умолчанию 64 |
| Максимум незавершённых подключений VPS | 2 × max_sessions |
| Виртуальные адреса на сессию | До 16 |
| Общий бюджет виртуальных адресов | 16 × max_sessions, в пределах доступного пула |
| Максимум одновременных подключений приглашения | Настройка записи; 0 — без ограничения приглашения |

Лимит адресов одной сессии не меняется при изменении вместимости сервера: вычисляется общий бюджет. Конфигурация проверяется относительно размера адресного пула и диапазона рабочих портов. Лимиты резервируются атомарно, чтобы параллельные подключения не обходили ограничения. Дубликаты управляющих запросов не занимают дополнительные места.

Ограничение приглашения относится только к одновременным подключениям. Нет регистрации или привязки устройств. Сессионный ID и секрет восстановления относятся к одному подключению и не являются постоянной идентичностью устройства. При снижении лимита работающие подключения сохраняются, а новые запрещаются до освобождения места. Отзыв записи закрывает её сессии немедленно.

Смена суток не завершает сессии. При смене NAT-привязки выполняется повторное защищённое подключение с восстановлением:

1. Клиент доказывает владение действующей сессией.
2. Сервер выдаёт новый рабочий сокет и свежие ключи.
3. Клиент подтверждает новый внешний адрес через новый рабочий порт.
4. Сервер сохраняет виртуальные адреса и conntrack, переключает ответы и закрывает старый сокет.

Восстановление заменяет прежнее логическое подключение и не должно требовать свободного места сверх его лимита; временные ресурсы ограничены лимитом незавершённых запросов. Обычная датаграмма без тега не меняет адрес получателя ответов. Сохранение внутренних TCP-соединений при восстановлении является целью; после перезапуска самого VPS оно не обещается.

При окончательном отключении, удалении записи клиента или тайм-ауте освобождаются ресурсы и удаляются относящиеся к виртуальным адресам записи conntrack. Адрес возвращается в пул только после успешной очистки и дополнительной выдержки две минуты. При ошибке очистки он остаётся недоступным для повторной выдачи. Повторное использование порта сопровождается новыми ключами, но не заменяет очистку NAT.

Входящий трафик без тега не доказывает владение ключом; привязка к исходному адресу и структурные проверки не являются криптографической авторизацией. Тайм-аут обновляют допустимые данные и keepalive от согласованного адреса, а также успешные аутентифицированные операции управления; пакеты от других адресов его не продлевают.

## Хранение и административные операции

Выбрана SQLite для записей клиентов и краткосрочной истории принятых запросов. База размещается в /var/lib/miga/ с правами 0600; права вспомогательных файлов SQLite также не должны раскрывать данные. Постоянные ключи сервера находятся в отдельном защищённом файле. Активные сессии и их ключи хранятся только в памяти.

Секреты для персонального HMAC должны быть доступны серверу в восстанавливаемом виде. Хранение одного необратимого хеша пароля не соответствует этой схеме. Секретные значения не попадают в логи, Git, публичные отчёты или установочные пакеты.

На Windows секреты хранит служба в %ProgramData%\MIGA: DPAPI с областью машины и ACL только для SYSTEM и администраторов. Agent передаёт приглашение через административный named pipe; обычный конфигурационный JSON содержит ссылку на профиль, а не секреты. На сервере операции выполняются через административные команды miga-server client add/list/revoke и изменение настроек, вызываемые Agent по SSH. Команда reset-device не нужна: регистрации устройств нет.

Имя записи, лимит одновременных подключений и отзыв управляются на сервере. Вывод персонального секрета допустим только как явный результат выдачи приглашения через административный канал, без записи в диагностический лог.

## Молчаливое отклонение и firewall

Требование защищает от активного сканирования и зондирования. Оно не мешает пассивному наблюдателю видеть легитимный обмен.

- Управляющий listener не отвечает на неизвестный формат, повреждённые сообщения, неуспешную предварительную проверку, неизвестного или отозванного клиента. Нет баннеров, открытых версий и диагностических ошибок.
- До успешной предварительной проверки не создаётся сессионный сокет. Ограничиваются вычисления, память и число незавершённых запросов.
- На рабочем порту пакеты от несогласованного внешнего IP/порта и пакеты с неверной структурой молча отбрасываются.
- Keepalive не получает ответа и не проходит в TUN.
- Подтверждение и восстановление внешнего адреса выполняются только защищённым управлением.
- Проверенные пользователи могут получать защищённые ответы об отказе по лимиту; это не открытый ответ постороннему трафику.

Firewall управляет только собственными цепочками и наборами MIGA:

- разрешаются действующие управляющие и сессионные порты;
- закрытые порты зарезервированного управляющего диапазона молча отбрасываются;
- недавно закрытые сессионные порты временно остаются в наборе молчаливого отбрасывания;
- сторонние UDP-службы и необходимые ICMP-сообщения, включая сообщения для MTU, не блокируются;
- политики основных цепочек и правила другого ПО не очищаются и не заменяются.

Перед резервированием управляющего диапазона проверяется конфликт с существующими службами. Полная невидимость всех свободных UDP-портов VPS не входит в задачу: это затронуло бы общую сетевую политику сервера. Закрываемый рабочий сокет удерживается две минуты в состоянии молчаливого отбрасывания, затем согласованно освобождаются порт и временные правила. Пока порт удерживается MIGA, другая служба не может занять его через bind().

Без тега сервер не может гарантированно отличить подделку от допустимых данных, если совпадают внешний адрес и проверки структуры. Для таких пакетов нельзя обещать отсутствие пересылки или косвенных ответов.

Оболочка скрывает открытые поля и начальные сообщения Noise. Размеры, интервалы, направления и последовательность обмена остаются наблюдаемыми. Отсутствие постоянного открытого маркера не гарантирует отсутствие статистической сигнатуры протокола.

## Переход на v2

Переход явный, без автоматического отката на старый протокол. Одновременное прослушивание старого raw-транспорта и нового протокола не предусматривается. После решения об удалении v1 поддерживается только v2; старые конфигурации отклоняются. Откат выполняется сохранённой версией исходников и бинарников.

Порядок после отдельного разрешения на реализацию и развёртывание:

1. Подготовить совместимые клиент, сервер и Agent.
2. Создать точку отката с бинарниками и конфигурацией, сохранив посторонние изменения.
3. Установить сервер с явным выбором режима.
4. Создать приглашение администратора для туннельного подключения и переключить обе стороны. Административные права по-прежнему определяются SSH-доступом.
5. Проверить трафик, диагностику и изоляцию клиентов.
6. При необходимости выполнить явный откат.

Правила выбора приложений, многосерверного DNS и диагностические функции сохраняются. Переработка транспорта не является разрешением изменить их поведение.

## Сознательно принятые ограничения

- У данных нет проверки подлинности и защиты от replay. Проверка формата IP и контрольных сумм их не заменяет.
- У 8-байтового случайного nonce возможны совпадения. При одном ключе вероятность хотя бы одного совпадения приблизительно 0,00027% после 10 миллионов пакетов и 2,67% после миллиарда. Повтор nonce повторяет шифрующую последовательность ChaCha20. Автоматическая смена ключей не вводится.
- Редкое совпадение управляющего порта в соседние дни разрешено.
- Хранение приглашения позволяет подключаться от имени записи до отзыва в пределах одновременных лимитов; аппаратной или постоянной привязки устройств нет.
- Шифрование, padding, смена порта и молчаливое отклонение не гарантируют обход DPI/ТСПУ. Видны адрес VPS и характеристики обмена.

## Согласованные детали спецификации

Решения этого раздела согласованы до реализации. Тестовые векторы, интеграционная сборка и испытания являются критериями приёмки, а не подтверждением уже работающего протокола.

### Приглашение

| Поле JSON | Тип и значение |
|---|---|
| v | Целое число 2 |
| host | IPv4-адрес или DNS-имя VPS |
| ports | Массив из двух целых чисел: начало и конец диапазона включительно |
| server_key | Открытый ключ сервера, 32 байта |
| server_secret | Общий секрет получения ключей расписания и оболочки, 32 байта |
| client_id | Случайный постоянный ID записи, 16 байт |
| client_secret | Персональный секрет, 32 байта |

Двоичные поля кодируются Base64URL без завершающего знака =. Весь компактный UTF-8 JSON кодируется тем же способом и получает префикс miga2:. Имени и лимита подключений в приглашении нет. Максимальная длина строки — 4096 символов. При импорте отклоняются дублирующиеся JSON-поля, неизвестная версия, некорректный диапазон и неверные размеры ключей.

### Бинарное управление

Заголовок и содержимое находятся внутри шифрования:

```text
version:     uint16
operation:   uint16
request_id:  16 байт
body_length: uint16
body:        body_length байт
padding:     оставшийся хвост
```

Version равен 2; целые поля имеют порядок big-endian. ID запроса случаен. Повторная отправка сохраняет ID и исходное содержимое операции; повтор не выполняет мутацию заново. Поля длины проверяются до чтения содержимого. Padding не является частью body.

| Код | Операция |
|---|---|
| 1 | HELLO |
| 2 | HELLO_REPLY |
| 3 | OPEN |
| 4 | OPEN_REPLY |
| 5 | BIND |
| 6 | READY |
| 7 | ADD_ADDRESS |
| 8 | ADDRESS_REPLY |
| 9 | RESUME |
| 10 | CLOSE |
| 11 | STATUS |
| 12 | ERROR |

Неизвестная операция не выполняется. Максимум управляющей UDP payload — 1200 байт. Типы операций, ID и версия не становятся открытой сигнатурой.

### Получение ключей и контекст

Используется стандартная схема HKDF-SHA256 Extract/Expand. Из общего секрета приглашений получаются отдельные ключи с метками miga-v2/schedule и miga-v2/envelope.

Для случайного 32-байтового секрета сессии применяются метки:

- miga-v2/data/c2s и miga-v2/data/s2c — ключи данных;
- miga-v2/prefix/c2s и miga-v2/prefix/s2c — префиксы nonce;
- miga-v2/control/c2s и miga-v2/control/s2c — ключи управления;
- miga-v2/resume — секрет восстановления.

Ключи имеют длину 32 байта, префиксы — 4 байта. Контекст получения сессионных ключей включает хеш завершённого Noise-handshake, ID клиента и случайный 16-байтовый ID сессии. Канонические байтовые представления контекста и параметров HKDF должны быть одинаковыми в клиенте и сервере и закреплены тестовыми векторами; новые криптографические конструкции при реализации не вводятся.

Персональный HMAC первого запроса вычисляется по однозначным бинарным полям с длинами: версия, ID клиента, время, ID запроса, ключ сервера и первое сообщение Noise. Padding не входит в смысловое содержимое HMAC, но защищён тегом внешней оболочки. Это связывает доказательство доступа с конкретным сервером и обменом.

### Управление сессией и подтверждение рабочего порта

После Noise используется общая обфускационная оболочка, внутри которой находятся ID сессии и сообщение, защищённое её персональным ключом управления. Знание общего секрета приглашений не даёт права изменять чужую сессию.

Для внутреннего управляющего сообщения применяется XChaCha20-Poly1305 со случайным 24-байтовым nonce. В защищённом содержимом находится 64-битный счётчик управления; окно защиты от повторов — 64 сообщения. Это не меняет согласованный формат данных: у данных нет счётчика, тега или replay-окна. Для повторной операции возвращается сохранённый результат, а не выполняется новая мутация.

Рабочий сокет имеет состояния:

1. Ожидание подтверждения: принимает только защищённый BIND.
2. Активная передача: принимает данные от согласованного внешнего адреса.
3. Карантин закрытия: молча отбрасывает входящие пакеты до освобождения порта.

BIND связан с ID сессии и случайным одноразовым вызовом из OPEN_REPLY. READY возвращается через защищённое управление. Если READY потерян, клиент запрашивает STATUS на управляющем порту. Активный рабочий сокет не пробует Noise или несколько вариантов AEAD для каждой датаграммы данных.

RESUME создаёт новый ожидающий сокет. Старый работает до успешного подтверждения нового, затем ответы переключаются атомарно. Допускается только одно незавершённое восстановление одной сессии. Виртуальные адреса и conntrack сохраняются, ключи и рабочий порт обновляются, старый сокет закрывается через состояние карантина. Восстановление занимает одно логическое место подключения, а не два.

### Время, история повторов и ограничения запросов

| Параметр | Значение |
|---|---|
| Допустимое расхождение времени первого запроса | ±120 секунд |
| Хранение принятых первых запросов | 10 минут |
| Максимум записей истории | 1024 × max_sessions |
| Новые допустимые handshake на VPS | min(max_sessions, 100) в секунду |
| Новые handshake одной записи клиента | 1 в секунду с кратковременным запасом 4 |
| Дешёвая предварительная проверка по исходному IP | 10 запросов в секунду с запасом 20 |

Ограничение по IP учитывает возможность нескольких пользователей за одним NAT. Повтор допустимого запроса не должен создавать новый handshake или повторно резервировать ресурсы.

Запись о принятом первом запросе сохраняется до первого ответа. Если SQLite недоступна или история исчерпана, новые подключения молча отклоняются; существующие сессии продолжают работать. Не допускается удалять ещё необходимые записи истории только ради приёма новых запросов.

После перезапуска история сохраняется, но ключи активных сессий не восстанавливаются. Записанные старые запросы отклоняются без ответа; клиент начинает новый обмен с новым ID. Пустой кэш ответов после перезапуска не превращает известный запрос в новый.

При существенном переводе часов назад новые handshake приостанавливаются до восстановления корректности времени, чтобы очищенная история не позволила повторное принятие старых запросов. Работающие сессии и их таймеры используют монотонное время. Проверка этого поведения включает перевод времени и перезапуск.

Повторные попытки управления используют интервалы 1, 2, 4 и 8 секунд со случайным отклонением ±20%. Повторяется исходная операция. Общий тайм-аут незавершённого подключения — 30 секунд.

Пятиминутный тайм-аут сессии обновляется допустимым пакетом данных или keepalive от согласованного адреса и успешной аутентифицированной операцией управления. Произвольный пакет от другого адреса его не продлевает. Keepalive без тега не доказывает владение ключом.

При снижении max_sessions или персонального лимита действующие подключения не разрываются. Новые не принимаются, пока число занятых мест не станет меньше нового предела. Нулевой лимит приглашения означает отсутствие персонального ограничения, но не отменяет max_sessions. Отзыв приглашения закрывает все его сессии немедленно. Регистрация устройств не вводится.

### Адреса, фрагменты и предельные размеры

ADD_ADDRESS передаёт локальный IPv4. Отображение индексируется по ID сессии и локальному IPv4. Повтор возвращает тот же виртуальный адрес даже с новым ID запроса. Адреса сохраняются до окончательного закрытия сессии, включая защищённое восстановление после смены NAT-привязки.

Внешние IP-фрагменты UDP собираются до расшифровки. Внутренние IPv4-фрагменты используют одно отображение адреса и маршрут независимо от наличия TCP/UDP-заголовка в конкретном фрагменте. Код не читает транспортный заголовок не первого фрагмента. После изменения IP пересчитывается его сумма; транспортная сумма корректируется только там, где её поле действительно присутствует. Длины и перекрытия проверяются до использования данных.

Максимальный внутренний IP-пакет без padding — 65499 байт: 65507 байт UDP payload минус 8 байт nonce. При превышении:

- если DF не установлен, выполняется стандартная IPv4-фрагментация внутреннего пакета; каждый фрагмент передаётся отдельной туннельной датаграммой;
- если DF установлен, пакет не обрезается и не отправляется; формируется допустимое правилами ICMP уведомление о необходимости уменьшить размер.

Это стандартная IP-фрагментация, а не собственный wire format фрагментов MIGA. Существующий механизм внешней фрагментации сохраняется. Тесты обязательно включают IP/TCP-опции, внутренние и внешние фрагменты, DF, PMTU и ошибочные длины. Поведение DNS, MSS и диагностического отключения переписывания MSS сохраняется.

### Firewall и освобождение ресурсов

Открытие рабочего порта выполняется в порядке: успешный bind(), подготовка состояния сессии, разрешение порта в собственной цепочке firewall, передача информации клиенту. При ошибке промежуточного шага ресурсы откатываются, клиент не получает неподготовленный порт.

При закрытии сокет две минуты удерживается в состоянии молчаливого отбрасывания. Только после выдержки освобождается порт и снимаются относящиеся к нему временные правила. Это предотвращает занятие порта другой службой, пока действует временный DROP MIGA.

Сокеты карантина не считаются активными сессиями, но имеют ограниченный бюджет ресурсов. При нехватке ресурсов безопасного открытия сервер отказывает новым подключениям, не вытесняя работающие. Технические пределы ресурсов должны быть явно зафиксированы и проверены в реализации.

При освобождении виртуального адреса:

1. Отключается его маршрут в сессию.
2. Удаляются только относящиеся к адресу записи conntrack.
3. Выдерживаются две минуты.
4. Перед возвратом в пул повторно проверяется и очищается остаточное состояние.
5. При любой ошибке адрес остаётся в карантине.

Выдержка является практической мерой, а не математической гарантией отсутствия любых запоздавших пакетов. Чужие conntrack-записи не удаляются. При конфликте подсети, диапазона портов или сетевых правил с AmneziaVPN чужая конфигурация автоматически не исправляется: выбирается допустимый ресурс либо установка останавливается с указанием конфликта.

### Зависимости, сборка и Windows-секреты

Исходная фиксация зависимостей:

- libsodium 1.0.22;
- Noise-C, ревизия cfe2541; полный SHA и контрольная сумма исходников записываются в манифест сборки перед интеграцией.

Библиотеки собираются статически для клиента и сервера. Автоматическое обновление зависимости при каждой сборке запрещено. Совместимость с Windows/Linux toolchain, тестовые векторы и упаковка проверяются при реализации; наличие библиотеки не считается доказательством интеграционной совместимости.

Windows-секреты хранит служба. Используется DPAPI с областью машины; файлы в %ProgramData%\MIGA имеют ACL только для SYSTEM и администраторов. Agent передаёт приглашение через административный named pipe. Конфигурационный JSON содержит ссылку на профиль, а не секреты. Область DPAPI машины не заменяет ACL: любой пользователь, получивший зашифрованный blob на этой машине, потенциально может вызвать его расшифровку.

## Критерии готовности спецификации к выпуску

Продуктовые и архитектурные решения зафиксированы. При реализации требуется закрепить совместные тестовые векторы сериализации, HMAC, HKDF, Noise и шифрования, полные контрольные суммы зависимостей и технические ресурсные пределы. Они не означают разрешения менять согласованные решения. Если интеграция обнаружит противоречие, его нужно вынести на обсуждение, а не молча менять протокол.

## Будущая проверка реализации

После отдельного разрешения проверить: TCP/UDP в обоих направлениях; нескольких клиентов и локальных IP с совпадающими портами; общий и персональный лимиты, включая 0, гонки подключения и освобождение мест без регистрации устройств; DNS через несколько VPS; короткие и повреждённые пакеты; padding/MTU/фрагменты; потери и перестановки; переход суток UTC и совпадение соседних портов; скачки часов; повтор и потерю handshake, в том числе через перезапуск; отзыв клиента с активными сессиями; смену NAT-привязки с сохранением внутренних потоков; остановку, перезапуск и reload; молчание приложения и отсутствие нежелательных ICMP на посторонние пробы; отсутствие секретов в логах; совместную работу с AmneziaVPN; скорость, потери и затраты ресурсов относительно текущего транспорта.

В рамках фиксации документа эти проверки не выполняются: реализация отсутствует.

# M.I.G.A. Android

Standalone Android Studio project. Open this directory, not the repository solution.

The Kotlin/Java compile toolchain is 17. The Gradle daemon uses JDK 25 as specified by `gradle/gradle-daemon-jvm.properties`; these are separate settings. Android SDK 37, Gradle 9.6.0 and Android Gradle Plugin 9.4.1 are pinned. Run `gradlew.bat :core:test :app:testDebugUnitTest :app:lintDebug :app:assembleDebug` on Windows.

## Release APK

From PowerShell in this directory, run `./release.ps1 -CreateKey` once, then `./release.ps1` for each signed release build. The script stores `release.p12` in the current Windows user's `.miga/android-release` directory outside Git and protects its randomly generated password with Windows DPAPI for that user. It runs `:core:test :app:testDebugUnitTest :app:lintDebug :app:assembleRelease` offline. Back up the keystore and its password separately: run `./release.ps1 -RevealPassword` privately to put the password in a password manager. The DPAPI file alone cannot recover it on another Windows account or computer. Future updates of the same application require the same signing key. The APK appears in `app/build/outputs/apk/release`; verify it with `apksigner verify --verbose --print-certs <apk-path>` from the installed Android SDK build-tools.

For manual signing, Gradle also accepts all four environment variables: `MIGA_RELEASE_STORE_FILE`, `MIGA_RELEASE_STORE_PASSWORD`, `MIGA_RELEASE_KEY_ALIAS`, and `MIGA_RELEASE_KEY_PASSWORD`. Supplying only some fails configuration. Without them, `assembleRelease` produces an unsigned APK. Do not commit signing material, local SDK paths, or APKs.

The four source-built `libhev-socks5-tunnel.so` ABI libraries must be present under `app/src/main/jniLibs` for DIRECT routing. If missing, run `./build-hev.ps1 -NdkPath <NDK-r30-path>` before Gradle. A successful APK build does not validate native loading or VPN traffic on a physical device.

The app has one IPv4 TCP/UDP VPN session with multiple simultaneous server transports. Create profiles with a public numeric server IPv4, UDP port range, and the existing server's Base64 keys (128 decoded XOR bytes and 8 decoded swap bytes). Assign each selected application to one profile. The active profile is the default for newly selected applications. Settings use a versioned DataStore document; version 1 selections migrate to the previous active profile while preserving profile IDs and secret references. Damaged or ambiguous settings are reported and kept. Secrets live in private no-backup files encrypted with AES-GCM under an Android Keystore key. Saved keys are not shown when editing a profile: use Replace saved keys to enter new ones. No automatic VPN start occurs after process restart. A missing or unreadable Keystore key requires entering the profile keys again.

Disconnect before changing profiles, assignments or the primary DNS profile. A profile with assigned applications cannot be deleted. The app lists launchable applications visible to Android, plus selected packages that have become unavailable. An unavailable selected package blocks connection until removed or restored. Every used profile must have an available secret. The service owns one TUN and a protected UDP socket for each used profile. The local tunnel state is separate from a valid server reply. A missing reply after outbound traffic is reported per server. No real end-to-end Android/server test is claimed by a successful APK build.

The TUN MTU, maximum complete inner IPv4 packet, and maximum legacy UDP payload are all 1400 bytes. Legacy encoding preserves packet length. TCP MSS is clamped to at most 1400 and to the remaining space after the actual inner IPv4/TCP headers. The outer IPv4/UDP headers add 28 bytes once, so a maximum packet may require 1428 bytes on the physical path. This is a size calculation, not a measured path MTU; outer fragmentation or path-MTU failure remains possible. Oversized packets and inner fragments are dropped with counters. The UDP receive buffer has one extra byte so an oversized datagram is rejected even if truncated by the receive call. The TUN uses nonblocking I/O with `poll` and a wake pipe for cancellation; the service retains the original descriptor while the packet engine owns a duplicate. IPv6 and excluded IPv4 routes bypass the tunnel in normal VPN mode; system lockdown can block bypass traffic. DNS is advertised as 1.1.1.1: the existing server redirects UDP port 53 to its configured `dns_server` when enabled, and rewrites the response source back to the original destination. TCP DNS is not redirected by that server setting. Mobile NAT and actual path MTU still require device tests.

Legacy wire format: the outer UDP payload is exactly one complete inner IPv4 packet. XOR repeats a 128-byte key, then adjacent swaps use the low-to-high bits of an 8-byte little-endian swap key XOR a 16-bit UDP destination port repeated four times. Replies use the server UDP source port as the nonce. There is no length prefix or authentication. The core API accepts port numbers in host order.

## Connection and lifecycle policy (stage 5)

The VPN service owns the session independently of the Activity. It does not auto-start after process death or reboot; Android always-on is disabled in the manifest. The foreground notification shows connecting, waiting, retrying, and local-running state and has a Stop action. Android 13+ asks for notification permission before starting. If permission is denied, Android can hide the foreground notification from the drawer while retaining it in the system Task Manager; Stop remains available in the app and system VPN controls.

A `NOT_VPN` internet network callback supplies both the initial network state and later changes, serialized on the main handler. Only validated Wi-Fi, Ethernet, and cellular networks are eligible, in that preference order. The current network is retained on an equal-rank tie; otherwise the lowest stable network handle breaks a tie. No arbitrary callback order determines the choice. A newly preferred physical network replaces each server's old transport even if the old network is still alive. Each replacement creates a new protected, network-bound UDP socket and invalidates that server's flow pins. `protect`, bind, and `setUnderlyingNetworks` must succeed before packet processing starts. Old callbacks and packet statistics are guarded by service and transport generation. Existing TCP connections may need to reconnect after an address or port change.

While no transport exists, the original TUN stays established. The single reader drains and discards captured packets immediately, with no replay queue; this prevents unbounded user-space buffering and direct fallback of selected public IPv4 traffic. Stop closes both descriptors and restores normal routing. A failed transport retries with capped exponential delay (1 to 30 seconds base, plus at most 20% jitter) only while an eligible network exists. There is one pending attempt per server at most. A successful local transport creation resets that server's backoff; it does not prove that the server is reachable. A valid decoded response for a pinned flow is the only server-reply signal. No heartbeat, wake lock, or battery-optimization exemption is used.

The inner packet/TUN MTU/UDP payload limit remains 1400 bytes, with a 1401-byte receive buffer for detecting overlong datagrams. Oversized and fragmented inner packets are dropped. Offline packets are discarded and counted as queue drops. Counters for active packet processing are scoped to each transport generation. Physical path MTU and Doze behavior have not been validated on a device.

## Multiple servers and ownership (stage 6)

One TUN reader dispatches packets to independent transport contexts. `getConnectionOwnerUid` is called off the main thread for new IPv4 TCP/UDP flows, and a bounded 4096-entry flow table pins each flow to a profile and transport generation for up to 120 seconds of inactivity. A bounded 1024-entry negative cache holds unresolved flows for 5 seconds. The exact five-tuple is used to associate replies with their originating profile and generation; replies from another server, an old generation, or an unexpected endpoint are rejected. UDP reply decoding uses the actual server source port as nonce. The single packet worker serializes TUN writes; its event queue has 128 slots and drops excess packets.

Packages sharing a UID must not have conflicting assignments: an ambiguous UID is rejected for ordinary traffic. An unknown UID, `INVALID_UID`, or a failed owner lookup also causes a drop with a diagnostic counter. There is no direct fallback or server failover. A failure of one transport leaves other transports active, with per-server status and counters. Network changes recreate the affected sockets and clear their flow pins; existing TCP sessions may need to reconnect. The TUN stays established while all transports are unavailable.

The selected primary DNS profile has an assigned application, IPv4 rule, or domain rule. Packets captured in the VPN for the advertised DNS address `1.1.1.1` on port 53 use this profile, including when Android attributes DNS to a system UID. Other traffic with unknown ownership is rejected. Per-app VPN behavior may prevent some system resolver packets from entering this TUN at all; that path needs device observation. SSH, hot reload, and automatic failover remain outside this stage.

## Static IPv4 rules: incomplete stage 7.1

Settings schema 4 stores stable UUIDs for static IPv4 and domain rules, profile IDs, canonical inclusive intervals, and a legacy capture-mode field for backward compatibility. Single addresses, CIDRs, and start-end ranges are accepted. Excluded IPv4 destinations and overlaps between different profiles are rejected. Earlier settings retain profiles, secret references, assignments, primary DNS selection, and the legacy field, which no longer selects the effective mode. A profile used only by a rule cannot be deleted and can be chosen as the primary DNS profile. Settings remain locked during VPN preparation and operation.

When the source-built DIRECT native library is available for the running ABI, the VPN captures public IPv4 from all applications and accepts any nonempty combination of application assignments, IP rules, and domain rules. Application assignments take priority over IP and domain rules, including UDP and TCP DNS traffic from the assigned application. Unmatched traffic from other applications uses DIRECT after a successful owner lookup; unassigned UDP DNS queries without a matching domain rule also use DIRECT. When DIRECT is unavailable, the VPN captures only assigned applications and requires an assignment; saved IP and domain rules remain available but inactive until DIRECT is available. IPv6 and excluded IPv4 routes retain their system routing policy; Android lockdown may block traffic outside the VPN. The service checks DIRECT availability again before establishing TUN.

The packet worker selects application assignment, then static IPv4 rule, then a DNS-derived IPv4 rule, then DIRECT after a successful owner lookup. Unknown/ambiguous UID is rejected. The advertised DNS address and port 53 retain a separate primary DNS route. Flows pin to server profile/generation or DIRECT generation; a failed server never becomes DIRECT. One real TUN reader dispatches DIRECT packets through a bounded queue and a separate `SOCK_SEQPACKET` pair to the native stack. Native replies re-enter the worker queue and its sole TUN writer. Old generation replies are rejected. The local SOCKS5 bridge uses authenticated loopback control, protected and Network-bound physical TCP/UDP sockets, finite session and destination caps, timeouts, and Stop/network-change closure. Its TCP and unconnected UDP paths have local loopback integration tests. None of these JVM tests proves the native Android path.

## Domain rules and DNS routing: stage 7.2

Rules accept an exact DNS name or `*.example.com`. Names are converted with IDN ToASCII, lowercased, and stored without a trailing dot. As in the Windows client, the wildcard includes the apex (`example.com`) and descendants on a label boundary, never `notexample.com`. Duplicate patterns and overlaps assigned to different profiles are rejected; row order has no routing meaning. Domain-only profiles are included in the session and can be the primary DNS profile. An APK without the source-built DIRECT library can start only with assigned applications; IP and domain rules become active when the library is available.

For observed UDP DNS on the advertised address, the packet worker registers one bounded query before sending it through the primary profile and copies with distinct wire IDs through the other active profiles. The primary response is delivered once with the application's original ID; auxiliary responses are consumed only for routing. The server's existing UDP/53 redirect and reverse source substitution remain in force. Responses are matched by transport generation, profile, full flow tuple, DNS ID, and question. The parser accepts bounded A/CNAME answer chains, multiple A records, TTL, NXDOMAIN, TC, compression, and unknown records. It rejects malformed messages. Only answer-section A records linked to the question can create routes; AAAA and unrelated additional records cannot. Cache entries use elapsed time and are capped at one hour even for larger advertised TTLs. TTL zero creates no positive route; a known ruled address is denied for ten seconds so it cannot fall through to DIRECT immediately. Existing flows keep their pinned route until flow expiry.

When a profile's DNS server returns a different A address, that address is used on the wire for its pinned flow. The outbound destination and inbound source, including IPv4 and transport checksums, are translated so the app continues to see the primary answer. Matching addresses in the two A sets retain identity even when answer order changes. A single unmatched address on each side can be paired; multiple unmatched addresses or unequal counts leave those visible addresses unresolved. A new incompatible mapping for the same domain, profile, and visible IP remains unresolved until its TTL expires, while established flows keep their pinned translation.

The cache updates one logical record per domain, profile, and visible IP and refreshes its TTL on identical replies. A domain rule is recorded from the primary answer even when its profile was unavailable at query registration, disconnected before the answer, or never replied. Its ordinary flow is denied until a compatible auxiliary answer arrives or the record expires; it cannot fall through to DIRECT. Up to 2048 full records and 2048 overflow denials are retained. Optional mappings for domains without a rule yield capacity to ruled addresses. Once full records are exhausted, only affected new ruled addresses are denied; unrelated IPs are unaffected. If both bounded tables fill with ruled addresses, a temporary global denial is necessary because further known addresses cannot be remembered individually. An exposed IP associated with different domain-rule profiles is ambiguous. This is IP-level routing: another hostname sharing the same IP, cached answers not seen by this VPN, DoH, and DoT cannot be attributed reliably. Such DNS is not decrypted or claimed as a domain match. Explicit app assignments and static IP rules retain priority; an assigned app uses its selected profile and the app-visible IP when no unambiguous DNS translation exists.

TCP/53 goes to the primary profile. A bounded length-prefixed observer handles split, reordered, duplicated, and wraparound TCP segments without modifying the application's TCP payload or sequence numbers. For a domain assigned to another active profile, a separate Android TCP socket sends the same DNS query to the advertised DNS address through this VPN's TUN. Its source port is registered before connect and pinned to that profile and transport generation. The helper sends no DNS payload unless its SYN was actually sent through that selected transport; late packets after detach cannot switch to the primary server. In Assigned apps mode, the VPN app is included in the allowed set for this purpose; physical tunnel and DIRECT sockets remain protected and Network-bound. The helper uses one DNS/TCP message per connection, at most 16 concurrent sockets, a 4096-byte reply limit and five-second connect/read timeouts. The primary response alone reaches the application; the helper response updates routing only after its token, generation, DNS ID, and question match. The existing server does not redirect TCP/53 to its configured `dns_server`, so both connections reach the advertised DNS address. TC alone adds no route. A known ruled address whose positive TTL expires remains denied rather than falling through to DIRECT; a later successful resolution can restore its route. The bounded cache may enter global fail-closed denial after both ruled-address tables fill. This path has JVM packet-engine checks but still requires physical device and two-server validation. DNS counters are sampled every five seconds.

The selected stack is [hev-socks5-tunnel 2.17.1](https://github.com/heiher/hev-socks5-tunnel/releases/tag/2.17.1), commit `9a06bc6e7989da54e3d32ff701ef7a7ce4995d3a`. Its Android API accepts an FD and supports IPv4 TCP and UDP. It is C/lwIP and **does not require Go**. The root and other hev components use MIT; bundled lwIP uses its BSD-style license. Notices are in `third_party/hev-socks5-tunnel`. The pinned source build is scripted in `build-hev.ps1`: it requires [Android NDK r30, 30.0.16248370](https://developer.android.com/ndk/downloads), clones the official tag and submodules, checks the commit, materializes source symlinks on Windows when needed, runs `ndk-build`, verifies arm64-v8a, armeabi-v7a, x86 and x86_64, and copies the libraries into ignored `jniLibs`. The script does not install SDK packages or accept licenses. An offline Gradle build without `.so` verifies Kotlin wiring only; native integration requires the ABI library and a device test.

Device validation matrix after the native build: assigned app TCP/UDP uses its profile; unassigned app matching an IP rule uses that profile; unmatched TCP/UDP exits directly; one server failure does not reroute its flows; Stop closes all sockets; Wi-Fi/mobile change closes old sockets and ignores old callbacks. Record actual server replies and direct endpoints on an authorized physical device. These scenarios have not been run.

### Physical device check matrix

Use a configured physical Android phone and a separately authorized test server. Record Android version, network type, device model, server port range, timestamps, and observed client/server counters without recording keys. For each case record success/failure and whether a valid server reply was observed:

| Case | Reproducible action | Expected observation |
| --- | --- | --- |
| TCP and UDP | Connect; run TCP upload/download and UDP echo in a selected app | Both directions work; valid reply counter advances |
| Wi-Fi to mobile and back | Keep VPN on while switching the preferred network twice | New underlying network and socket; existing TCP may reconnect; no direct fallback |
| Airplane mode | Enable, then disable airplane mode | Waiting without retry polling; automatic local reconnect after validation |
| Screen off and Doze | Transfer with screen off; enter device idle using Android test commands if permitted | Record transfer, delay, and battery behavior; no claim based on emulator |
| Unreachable server | Point test profile at an authorized unreachable endpoint | Local-running or no-response state; no false server-reply claim |
| Stop during retry | Disconnect while retry is pending | TUN and timer close; no late restart |
| Restart | Connect, Stop, then connect again | One session each time; no duplicate notification or socket |
| App restart | Save profile; close and reopen Activity/process without VPN autostart | Profile and selection persist; manual Connect required |
| Two applications, two servers | Assign two test apps to distinct profiles, set primary DNS explicitly, then run TCP and UDP concurrently | Each server sees only its assigned app flows; both receive valid replies |
| Shared UID | Assign packages sharing a UID to different profiles, then send ordinary traffic | No arbitrary server selection; unknown or ambiguous owner drop counter advances |
| One server failure | Disconnect one authorized test server while both apps transfer | Other server continues; failed app neither falls back nor changes server |
| Network change with two servers | Switch Wi-Fi to mobile and back during concurrent transfers | Both transports recreate; old replies are rejected; TCP may reconnect |
| Domain-only profile | On public capture with a source-built DIRECT library, assign `*.example.com` only to server B; resolve through primary A | Primary DNS reply appears once; A's and B's DNS answers and the selected packet destination are recorded; matching TCP/UDP uses B |
| Different A answers | Resolve the same name on A and B when they return different public A records | App sees A's answer; B receives traffic for B's address; app sees responses from A's address with valid checksums |

| TCP DNS fallback | Force TC on UDP, then use DNS/TCP with split, reordered and repeated segments, and multiple queries on one application connection | No route is claimed from TC; the primary answer appears once; a matching auxiliary TCP answer opens the secondary route; absent or stale auxiliary answers keep it denied |
| Encrypted or cached DNS | Use DoH/DoT or an OS-cached answer unseen by the VPN | Domain route is not claimed; application and static IP priorities remain effective; record actual fallback behavior |

Installation, real network traffic, mobile NAT, path MTU, and Doze observations require an authorized device and server. JVM tests and APK compilation do not establish those results.

# NETWORK runtime

Рабочее ядро Windows-клиента — `NetworkRuntime`, подключённое к `CMigaClient`. Прежнее ядро удалено из проекта; общие типы tuple, TCP и маршрута, а также парсер пакета находятся в PacketTypes.h. ConfigManager только загружает конфигурацию, индексы маршрутизации принадлежат новому ядру. Поддерживается только protocol=2: асинхронные ProtocolV2Session и профили DPAPI. Согласованный проект — PROTOCOL_V2_DESIGN.md, канонические байты и границы реализации — PROTOCOL_V2_IMPLEMENTATION.md.

Объявления классов находятся в include, реализации — в src с той же структурой подкаталогов. Внутреннее состояние NetworkRuntime::Impl объявлено в src/NetworkRuntimeImpl.h, методы определены в src/NetworkRuntime.cpp. Шаблонные методы остаются в заголовках для инстанцирования вызывающим кодом.

Стартовые снимки TCP/UDP и первоначальная подготовка транспортов выполняются до NETWORK-перехвата. SOCKET уже подписан и принимает события во время снимка. Существующие TCP-сеансы сохраняют прямой маршрут. Системные вызовы подготовки могут задержать запуск; уже выполняющийся Windows API нельзя отменить при Stop.

## Быстрый путь

NETWORK владеет двумя приёмными буферами по 256 КиБ и заранее запускает следующий приём. Известный прямой пакет попадает непосредственно в накопитель асинхронной отправки. Известный туннельный пакет преобразуется непосредственно в приёмном буфере и передаётся в накопитель внешних датаграмм. Межпоточной очереди этих пакетов и отдельного туннельного потока нет. Накопленные отправки завершаются в конце полученной пачки без ожидания следующей.

IPv6, неподдерживаемые протоколы и DHCP 67/68 исключены фильтром и остаются в стеке. Private, loopback, link-local, multicast и broadcast IPv4 идут напрямую. NETWORK открыт без `WINDIVERT_FLAG_FRAGMENTS`: входящие фрагменты собирает Windows до перехвата. Это поведение требует проверки с реальным драйвером на целевой машине.

В раздельном режиме (`routing_mode=split`, по умолчанию) действуют правила приложений, IP и доменов включённых серверов. ConfigManager исключает записи с `enabled=false` до загрузки профилей и подготовки транспортов. Отсутствующее поле означает `true`. Когда все серверы выключены, новые потоки идут напрямую и синтетический DNS выключен. В полном (`routing_mode=full`) `full_routing_profile_id` выбирает одно подключение. Весь перехваченный публичный IPv4 TCP/UDP, включая DNS к публичному резолверу, направляется туда без классификации по владельцу и без прямого резерва. Корректные DNS-запросы UDP/53 к частному IPv4 (RFC 1918) тоже идут через выбранный сервер. Точные служебные UDP tuple транспорта пропускаются напрямую, включая сеансы, подготавливаемые при reload. При смене режима или выбранного VPS старые маршруты и отложенные пакеты сбрасываются. Уже открытые соединения могут потребовать переподключения.

Обе отправки используют отдельные пулы по 32 overlapped-операции. Буферы, адреса и OVERLAPPED живут до завершения/отмены. Насыщение пула учитывается в `send_pool_full`; гарантий доставки при перегрузке нет.

## Состояние и ожидания

- `SocketDirectory`: до 8192 владельцев, индекс по протоколу/локальному порту, shared_mutex для коротких чтений и изменений. Записи неизменяемы, активность и границы жизни атомарны. При заполнении сначала вытесняется самый давно закрытый владелец; при отсутствии закрытых записей новый владелец не добавляется. Это не удаляет сохранённый TCP-маршрут.
- `FlowTable`: до 65536 полных tuple, единственный владелец NETWORK. На пакете обновляется активность, но таймер не переставляется. Версии портов позволяют обходиться без поиска владельца для обычного пакета известного соединения. Обратная DNS-подмена индексируется по серверу и полному tuple, а не глобально по IP. Неоднозначное совпадение двух преобразованных tuple не разрешается созданием второго маршрута.
- CLOSE оставляет владельца на 30 секунд. TCP-маршрут независим от удаления владельца: ACK и SYN с сохранённым sequence продолжают использовать маршрут. Если SYN использовал BIND, единственный точный CONNECT того же экземпляра процесса между BIND и SYN уточняет владельца без смены маршрута и поколения. Ненулевой ParentEndpointId должен совпасть с BIND. Для нового подключения после SYN смена EndpointId означает новое поколение даже с тем же sequence. Ожидание другого SYN не блокирует ACK сохранённого поколения.
- TCP: 124 минуты простоя, после RST/двух FIN — 4 минуты. UDP: 20 минут. Открытый давно неактивный TCP проверяется в Windows. Ответ проверки сверяется по ID, попытке, активности и CLOSE/cutoff; ошибка снимка не означает отсутствие соединения. Повторная успешная проверка через 60 секунд, ошибка/непереданное задание — через 30 секунд.
- Неизвестный владелец: до 1024 пакетов / 4 МиБ, индивидуальный срок 5 секунд. Новое соединение без сохранённого маршрута после срока отправляется напрямую. Неопределённое новое поколение известного TCP и UDP с прежним туннельным маршрутом отклоняются. Решения классификатора проверяются повторно по текущему владельцу и версии конфигурации.
- Временно недоступный исходный адрес/MTU: отдельное ограниченное ожидание до 1024 пакетов / 4 МиБ / 5 секунд. Оно сохраняет порядок пакетов одного сервера; готовые серверы продолжают работу.
- Межпоточные очереди передают задания/результаты: NETWORK 2048, классификатор 1024, SOCKET и Windows по 128. DNS-пакеты также проходят классификатор. Очереди ограничены числом заданий; эти лимиты не являются общим пределом памяти процесса. NETWORK не ждёт свободного места при передаче задания. При временном насыщении классификатора запрос повторяется.

Блокировки очередей освобождаются до выполнения задания. Под блокировкой SocketDirectory не отправляются задания и не вызывается Windows API. Таблицы маршрутов и DNS не имеют вложенных межпоточных блокировок: каждый набор изменяет только его владелец. PacketBufferPool используется только для пакетов, которым требуется отдельное время жизни.

## DNS и reload

При выключенном локальном резолвере прямой входящий DNS-ответ возвращается в стек сразу и без изменений. При наличии явных доменных правил его копия передаётся классификатору для изучения адресов; отказ этой очереди фиксируется как dns_observation_rejected и не отбрасывает сам ответ.

В раздельном режиме DNS-запросы UDP/53 к частным IPv4 проходят тот же выбор по правилу процесса и имени вопроса, что и запросы к публичному резолверу. Без совпадения запрос уходит на исходный резолвер напрямую. VPS перенаправляет туннелируемые запросы к частному резолверу на `dns_server` или на `8.8.8.8`, если настройка пуста. Обратный NAT восстанавливает исходный адрес резолвера.

Правило приложения направляет DNS через его сервер, но не создаёт глобальное правило по полученному IP. Глобальные IP возникают только из DNS-ответа с именем вопроса, соответствующим явному redirect_domains. Основной и вспомогательные запросы получают уникальные wire ID; основной ответ восстанавливает ID приложения, вспомогательные ответы не попадают в стек. Соответствия учитывают несколько A-записей, порядок ответов и TTL обеих сторон. До 8192 незавершённых wire ID, до 65536 динамических записей и до 65536 соответствий адресов; переполнение отражает `dns_capacity_exceeded`.

### Синтетический IPv4 DNS

В раздельном режиме локальная обработка обычных IPv4 UDP-запросов A к порту 53, включая запросы к DNS роутера, включена по умолчанию. Параметр `dns_resolver_enabled: false` отключает её. В полном режиме встроенный резолвер выключен. Одноуровневые имена, зоны `.local`, `.localhost`, `.home.arpa`, loopback, DNSSEC-запросы и неподдерживаемые форматы следуют прежнему пути. DNS по TCP, AAAA, DoT и DoH не проходят через синтетический резолвер.

В раздельном режиме классификатор при каждом новом A-запросе Windows запрашивает имя напрямую и через каждый настроенный VPS. Для ответа Windows используется выход, заданный правилом процесса-владельца DNS-сокета. Без совпадения правила запрос ждёт прямого DNS. Для системного DNS владельцем сокета обычно является DNS Client Windows. При повторных запросах, пока ответ конкретного выхода в пути, клиенты разделяют запрос к этому выходу и получают ответы со своими DNS ID. Как только выбранный DNS отвечает, классификатор возвращает синтетический IPv4. Ответы других выходов обрабатываются независимо.

Привязки имя → адрес из 198.18.0.0/15 хранятся в памяти службы. Адрес 198.18.0.1 зарезервирован для диагностического UDP-ответчика и исключён из выдачи и подмены. TTL синтетической записи равен минимальному TTL пригодных A-записей выбранного выхода. При NXDOMAIN или NOERROR без A выдаётся синтетический IP с отрицательным TTL из SOA либо с TTL 0. NXDOMAIN записывается как WARNING. Последние результаты каждого выхода хранятся до обновления, применения конфигурации или вытеснения из ограниченного кеша. Повторный запрос Windows обновляет результаты. В полном режиме встроенный резолвер выключен и DNS обрабатывается правилами полного режима. После выключения резолвера в текущем сеансе службы блокируются ранее выданные синтетические адреса.

Запросы отправляются с отдельного зарезервированного UDP-порта и случайными DNS ID, с EDNS0 и размером UDP 1232 байта. Ответ сверяется по вопросу, полному tuple и VPS. Классификатор хранит до 2048 запросов к выходам, 512 ожидающих DNS-ответов приложений и 2048 последних результатов. При отсутствии ответа через 2 секунды отправляется один повтор на том же выходе с тем же DNS ID. Общий срок ожидания ответа остаётся 4 секунды от первой отправки. При таймауте, TC или ошибке выбранного DNS клиент получает SERVFAIL. Новый поток выбирает маршрут по порядку процесс → статический IP → домен → напрямую. При наличии статических IP-правил выбор после проверки процесса требует результата прямого DNS. Пакет ждёт до 5 секунд, если выбранный выход ещё разрешает имя. При отрицательном результате или истечении ожидания пакет отбрасывается без обхода. Для прямого маршрута допускается RFC 1918, для туннельного нужен публичный IPv4.

NETWORK закрепляет реальный адрес и прямой или туннельный маршрут в FlowTable. Исходящие пакеты получают реальный адрес, входящие восстанавливают синтетический адрес по полному tuple и VPS или прямому каналу. Для прямой передачи клиент обновляет подтверждённые WinDivert контрольные суммы по разнице адресов. При неподтверждённой сумме, после сборки фрагментов или при других изменениях выполняется полный пересчёт. В туннеле внутренняя сумма всегда пересчитывается целиком. Пакеты установившихся соединений не требуют DNS-заданий или дискового доступа. Коллизия преобразованных tuple блокирует создание второго маршрута. Переключение режима резолвера сбрасывает накопленные маршруты, поэтому активные соединения могут потребовать переподключения.

При запуске или перезагрузке конфигурации имя VPS сначала проверяется по файлу Windows hosts. Если включён синтетический резолвер или зарезервированы ранее выданные адреса, клиент разрешает имя нового VPS через настроенный Windows IPv4 DNS, минуя системный DNS-кеш. Запрос службы использует временный зарезервированный UDP-порт и проходит напрямую даже в полном режиме. Это позволяет установить туннель до того, как через него станут доступны DNS-запросы приложений.

Reload подготавливает конфигурацию и транспорт до публикации. Неизменившиеся IP/порты/ключи сохраняют транспорт и стабильный ID. NETWORK приостанавливает обработку новых пачек и ждёт завершения старых отправок, затем атомарно публикует конфигурацию. Старые результаты классификации не применяются к новой версии. Удалённый транспорт делает существующие маршруты недоступными, без автоматического перехода напрямую. Уровень логирования меняется без повторного открытия и обрезания файла. После успешной публикации, после запуска перехвата и после его остановки служба очищает системный DNS-кеш Windows. Отказ очистки при запуске или перезагрузке отмечается событием `dns_cache_flush_failed`.

Stop будит ожидания, закрывает межпоточные очереди, завершает потоки, отменяет и завершает I/O до закрытия WinDivert handle. При необработанной ошибке NETWORK/SOCKET остальные потоки получают сигнал остановки; служба выходит из рабочего цикла без автоматического перезапуска.

## Диагностика и проверка

`runtime_queue_delay` показывает ожидание задания от постановки до извлечения, порог 100 мс, отдельно для каждой очереди. Оно не включает пятисекундное ожидание владельца. `batch_processing` относится к обработке принятой NETWORK-пачки. `runtime_drop` содержит причину и число отказов; время префикса — первый отказ этой группы. `send_pool_full` считает отклонённые операции, которые могут содержать несколько пакетов. `route_created`, `packet_received`, `route_lookup`, `socket_event`, `pending_timeout` и `runtime_counters` доступны в DEBUG. `socket_event` и `route_created` рядом с PID указывают имя исполняемого файла владельца сокета (`process`), если оно известно. `socket_owner_capacity` сообщает об отказе добавить владельца при заполнении таблицы открытыми записями. Старые `event_queue_delay type=NETWORK` и `tunnel_queue_full` относятся к прежнему PacketMonitor.

Тесты и команды — в [tests/README.md](tests/README.md). Проверки с подменёнными WinDivert API не подтверждают работу настоящего драйвера, стартовые гонки снимка, фактическую доставку или выигрыш производительности. Для сравнения нужны одинаковые живые прогоны UDP, churn и обычного TCP/DNS-трафика.

## Диагностический сеанс

DiagnosticSession обслуживает отдельный локальный административный named pipe MigaDiagnostics-v1. Helper подтверждает временный маршрут экземпляра процесса и регистрирует тестовые сокеты до открытия соединений. Сеанс и наблюдения ограничены по ёмкости, закрытие pipe снимает временные настройки. Обычный пакетный путь при отключённом сеансе проверяет атомарный флаг; диагностические таблицы, строки и блокировки не используются. DF-пробы передаются TunnelDatagram без ручной фрагментации, с установленным внешним DF; поля MSS тестовых потоков можно временно пропустить в обоих направлениях. Точная схема, управление TLS и ограничения измерений описаны в DIAGNOSTICS.md.

Прямой STUN-пинг регистрирует один IPv4 UDP tuple через тот же административный канал до первого пакета и без серверного сеанса. Поток канала проверяет PID и локальный сокет по снимку UDP Windows до захвата mutex DiagnosticSession. NETWORK проверяет атомарный порт и только при совпадении берёт этот mutex для сверки полного tuple и живого процесса. Совпавший трафик уходит в reinject в обоих направлениях до выбора маршрута, в том числе в полном режиме. Завершение пробы или разрыв канала снимает обход. При Stop NETWORK завершается до остановки DiagnosticSession.

Диагностический параметр `sequence_port` включает для одного UDP-порта сессии учёт уникальных 16-битных номеров в payload длиной ровно 2 байта. `captured_sequences` фиксируется при NETWORK-перехвате, `completed_sequences` — только после успешного завершения WinDivertSendEx той же сессии. Номера не должны повторяться в прогоне. Учёт выключен по умолчанию; наборы ограничены пространством 65536 номеров и очищаются при завершении шага/сессии.

## Protocol v2

Каждый Transport protocol=2 владеет ProtocolV2Session. Его отдельный поток выполняет Noise и защищённое управление; NETWORK читает immutable snapshot без блокировки управляющего обмена. Локальный резервирующий UDP-сокет используется для BIND/keepalive, обычные данные сохраняют WinDivertSendEx. Исключение служебного трафика проверяет точный UDP tuple и направление; IP VPS целиком не исключается.

Уведомления IP Helper инвалидируют кеш, а поток Windows API заново разрешает путь до каждого VPS. NETWORK запрашивает RESUME при изменении исходного IPv4, LUID интерфейса или следующего узла и применяет новый MTU независимо от RESUME. При временной недоступности пути последний успешный путь сохраняется для сравнения после восстановления.

После сна Windows длительностью от пяти минут управляющий поток сразу пробует RESUME даже при прежнем пути. Длительность определяется по системным счётчикам времени с учётом и без учёта сна. При первой неудаче клиент сбрасывает прежнюю сессию и начинает новый HELLO. Если подтверждение уже ожидалось в момент сна, клиент проверяет STATUS и при первой неудаче открывает новую сессию.

При отсутствии готовой сессии или адреса пакет помещается в отдельную очередь до 1024 пакетов/4 МиБ/30 секунд. Переполнение и истечение приводят к drop. Первый локальный IP выдаётся при подключении, следующие через ADD_ADDRESS. Подмена адреса выполняется после выбора исходного flow и корректирует checksum; обратная подмена предшествует обработке DNS/flow. Сессионный серверный порт проверяется точно, диапазон управления не используется для данных.

Фрагменты собираются до разбора транспортного заголовка; собственный формат фрагментов не вводится. Reassembler имеет лимиты 1024/4 МиБ/30 секунд и отклоняет перекрытия. Периодическая сводка оставляет очередь ожидания сессии и оба сборщика фрагментов до их штатного обслуживания или остановки. Пакеты больше 65499 байт фрагментируются стандартно либо возвращают ICMP при DF. Padding ограничен MTU; MSS учитывает 36 байт внешнего транспорта и фактические внутренние заголовки.

Перед заменой конфигурации завершаются обе группы WinDivert-отправок. Неизменившийся profile_id сохраняет транспорт; уничтожение Transport останавливает control worker до закрытия резервирующего сокета. Stop завершает NETWORK, отправки и workers до WSACleanup. Профили импортируются только через административный MigaProfiles-v2; JSON содержит ссылку на профиль.

Для v2 EncryptDataInto шифрует исходный пакет непосредственно в payload TunnelDatagram::BuildGenerated. Промежуточного encryptedV2 нет. Копирование в принадлежащий AsyncTunnelSender буфер сохраняется до завершения overlapped I/O; формат пакета и фрагментация не изменены.

Диагностика v2: MigaProfiles-v2 выдаёт параметры TLS через текущую сессию профиля. ProtocolV2Session имеет один ожидающий запрос DiagnosticOpen, который исполняется только потоком управления с дедлайном 8 секунд. NETWORK не ожидает результата, секреты приглашения Agent не получает. DiagnosticSession выбирает профиль по profile_id; без ready-сессии возвращает local_only и наблюдает обычную классификацию без принудительного маршрута. Helper пропускает все серверные проверки, включая скорость, без подтверждённой авторизации. Выбор только capture/route не открывает серверный канал. Каждый из этих шагов открывает отдельный интервал наблюдения за выбранным экземпляром процесса. Для активной пробы проверяется также tuple зарегистрированного сокета и адреса назначения. Capture подтверждается перехватом, route — зафиксированным решением маршрутизации, а для принудительного туннеля проверяется ID выбранного сервера.

### Счётчики обычной диагностики

Обычная диагностика считает captured/unowned во внутренних перехваченных пакетах. submitted считает попытки передачи внешних пачек через SendObserved для TCP и UDP; одна пачка может содержать несколько IPv4-фрагментов. completed увеличивается только после успешного полного завершения отправки, send_rejected включает немедленную ошибку, переполнение и отмену; pending = submitted - completed - send_rejected. Отказ до формирования отправки учитывается отдельно в pre_send_rejected. send_counter_unit имеет значение outer_send_batches; эти величины нельзя напрямую сравнивать с captured. Идентификатор сеанса исключает завершения прошлой регистрации. При выключенной диагностике наблюдаемые отправки не включаются.

### Счётчики нагрузочной диагностики

Shared/DiagnosticLoad хранит ограниченные битовые карты по run/step/direction/sequence. DiagnosticSession включает их только по административному запросу load_configure; load_stop, finish_step и завершение сеанса очищают состояние. NETWORK отмечает перехват, выбор туннеля и получение ответа, callbacks асинхронных отправок — фактическое завершение WinDivertSendEx и reinject. Callback сохраняет идентификатор пробы, поэтому завершение предыдущей ступени не загрязняет следующую. Неактивный счётчик проверяется атомарно, не выделяет память и не форматирует сообщения. Mutex счётчиков не вызывает методы DiagnosticSession или NetworkRuntime; обратного порядка блокировок нет. Полезная нагрузка и транспорт не копируются ради учёта.
